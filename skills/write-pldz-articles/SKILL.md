# PLDZ 技术实践文章写作

## Overview

把文章写成“我做过这个东西，顺手记录一下怎么用、怎么实现”的开发记录。不要把原始内容包装成一篇完整、漂亮、四平八稳的产品说明。先看文章到底属于哪一类，再决定开头和章节；能从输入材料读出来的就写，材料里没有的动机、效果、测试结论和后续规划不要自行补出来。

需要详细的风格画像、常用表达和文章结构证据时，阅读 [references/style-profile.md](references/style-profile.md)；需要判断文章属于工具分享、技术文章、教程还是项目介绍时，阅读 [references/article-modes.md](references/article-modes.md)。在当前项目中有原始文章时，优先抽样阅读 `data/articles` 下的文章，但跳过 `data/articles/cloud-service`；`ABOUT.md` 只用于了解栏目命名，不作为正文语气的主要样本。

## 文件工作流：`INPUT.md` → `OUTPUT.md`

当用户要求“读 `INPUT.md`，输出 `OUTPUT.md`”时：

1. 先完整读取 `INPUT.md`，包括目录树、命令、版本、测试状态、限制和英文原文中的语气，不先凭项目名猜文章内容。
2. 判断主类型和副类型。项目 README 既可能是项目介绍，也可能需要改成工具分享或教程；以读者看完后的动作和输入材料的重心为准。
3. 只抽取输入里已经出现的事实、代码、命令和限制。可以把英文重新组织成中文，但不能为了“像文章”新增没有来源的经历和结论。
4. 先写一个粗的文章骨架，再填入原始材料。不要先写一段通用的开场白；开头必须从这个项目实际做了什么、怎么用或为什么做开始。
5. 将结果写入用户指定的 `OUTPUT.md`。保留有价值的命令、代码、目录树和测试条件；把 README 的产品化宣传句改成直接的开发记录。
6. 写完后从头检查：是否出现输入里没有的内容，是否把“未测试”写成“支持”，是否为了完整而加入了漂亮但没有信息量的总结段。

除非用户明确要求，不要修改 `INPUT.md`，也不要因为 `OUTPUT.md` 已经存在就顺手改动其他文章。

## 工作流程

### 1. 先判断文章类型，再确定要记录什么

不要因为主题是 Docker、ROS2 或 Python，就直接套同一个结构；先判断读者看完后要做什么：

- 想把一个脚本、插件、工具装起来并马上使用：**工具分享型**。
- 想理解一个机制、API、设计或实现方式：**技术文章型**。
- 想从零跟着命令和代码完成一个结果：**教程型**。
- 想先看看你做了什么、效果怎么样、源码在哪里：**项目介绍型**。

前三类是主要写作模式，项目介绍型可以独立使用，也可以和工具分享型或教程型组合。具体的判断信号、结构差异和样本映射见 `references/article-modes.md`。

- 用一两句话说明实际场景、遇到的问题和现在做了什么。优先使用输入材料里的具体说法，例如“因为在做 aigc 的服务免不了出现代理的情况, 所以用 Python 的 `aiohttp` 库来实现一个简单的全代理服务器”。不要把它改写成抽象的“本文旨在……”。
- 记录操作系统、软件版本、硬件、依赖、目录或网络前提；不确定的版本不要猜，标成待确认。
- 选一个具体可验证的结果作为主线：能启动、能看到页面、能发布消息、能生成文件、能跑通 demo 等。

### 2. 按文章类型组织正文

- **工具分享型**：问题/使用场景 → 快速体验 → 功能或选项 → 安装/配置 → 使用示例 → 限制和适用场景。
- **技术文章型**：问题背景 → 最小概念模型 → 实现方案 → 完整代码或关键代码 → 关键点/取舍 → 验证 → 总结。
- **教程型**：前置条件 → 第一步 → 中间检查点 → 第二步 → 预期结果 → 常见问题 → 总结；每一步都写清楚“在哪里执行”和“成功后看到什么”。
- **项目介绍型**：前言 → 效果预览 → 源码/在线地址 → 技术实现 → 核心功能 → 项目结构 → 当前完成内容和后续计划。

写作时可以有混合模式，但必须有一个主模式。例如“Python 代理服务器”是技术文章型为主、工具分享型为辅；“Ubuntu 配置与 ROS2 快速体验”是教程型为主、技术文章型为辅；不要同时把四种文章都写成同样长的概念解释。

章节标题可使用已有系列的编号（如 `2.1`、`2.2.1`），也可使用带少量 emoji 的自然标题（如 `## 😎 体验预览`、`## 🔧 脚本源码`）。技术系列优先保证编号连续、层级清楚；不要为了形式强行补齐没有内容的章节。

### 3. 用 PLDZ 的叙述方式解释

- 采用第一人称或面向读者的口吻，适度使用“这里”“那么”“其实”“直接看代码吧”“简单体验”“快速体验”“如下所示”等连接语，让文章像开发过程中的记录。不要为了显得像人而每段硬塞口头禅。
- 先说选择和动机，再说步骤；不要只罗列命令。例如说明为什么选 Python、为什么需要 Docker、为什么采用某一种通信方式。
- 保留中英文技术词混排和反引号标记：`ROS2`、`CMakeLists.txt`、`docker run`、`stream`。命令、路径、变量名始终用行内代码或代码块。
- 解释保持实用：先给完整可运行版本，再拆解真正影响理解的几个关键点。不要把每一行都改写成教科书定义。
- 口语可以自然、轻松，允许少量“没啥好说的”“话不多说，直接上结果”这类表达；不要堆砌网络流行语、营销话术或无意义 emoji。
- 用“参考内容”区块放官方文档和实际参考链接；引用别人的结论时标明来源，不把未验证的内容写成自己的实测结果。

#### 特别重要：不要生成“总结得很好的 AI 句子”

你的原文经常是直接把版本、命令、代码和现象写出来，不会每段都替读者提炼一个完整观点。不要擅自补下面这些腔调：

- “这个项目的目标不是……而是……”
- “通过……可以……从而……”
- “这样设计的好处是……”
- “这为后续……打下了基础 / 方便后续继续扩展”。
- “这套方案能够有效……”或“整体上实现了……”
- “对于……来说，这是一个……”
- “当前这些限制并不影响……如果要做成通用工具……”
- “本文将详细介绍……”、“总的来说，这篇文章……”

除非 `INPUT.md` 本来就明确这样说，否则不要使用这些句式。少写一句抽象总结，通常比多写一句漂亮话更像原文。

例如，下面这段比较像 AI 生成的项目介绍：

> 这个项目暂时只在 Ubuntu X11 环境中测试过。它的目标不是做一个完整的语音助手，而是先把“按住说话，松开就输入”这条链路跑通，方便后面继续扩展。

如果输入材料只提供了测试状态和操作方式，改成直接记录：

> 目前只在 Ubuntu X11 下测试过，Wayland 还没有支持，其他 Linux 发行版也没有测试。按住 `Ctrl+Win` 开始录音，松开任意一个按键停止，最后把识别到的文字插入之前的输入位置。

这不是要求故意写错或故意变得粗糙，而是不要主动添加“目标—价值—未来”的完整叙事链。

### 4. 给出可以复现的材料

- 优先提供完整的最小示例、目录树、安装命令、配置文件和运行命令；需要多个文件时按文件名分段给出。
- 对终端输出、报错和效果截图保留上下文，说明它代表什么；如果当前没有真实截图，就写“预期效果”或留出图片位置，不能伪造结果。
- 每个关键步骤后补一个验证动作：查看版本、列出话题、访问地址、检查生成文件、观察日志或运行一个最小测试。
- 对有破坏性的命令、权限操作、密钥、代理地址和真实路径使用占位符，并明确哪些值需要读者替换。

### 5. 做一次“像不像”和“能不能跑”的检查

- 语气检查：是否有个人实践动机、是否像在带人做一次实验、是否避免了过度正式的“本文将深入探讨”腔；逐段删除没有提供新事实、命令、代码或判断的总结句。
- 结构检查：读者能否从前言知道目标，从步骤知道下一步做什么，从结果知道是否成功。
- 技术检查：命令、包名、文件名、版本、代码和标题是否一致；明显拼写错误可以修正，但不要为了“完美”抹掉个人语气。
- 事实检查：把“我验证过”“官网这样写”“理论上支持”“尚未测试”分开写；当前版本、价格、API 或系统行为有变化可能时先核实。
- AI 腔检查：搜索并重新审视“目标不是”“从而”“因此”“这样设计”“方便后续”“打下基础”“整体来看”“值得注意”“适合用来”等连接词；它们不是绝对禁用，但如果删掉不影响事实，删掉。
- 输出检查：Markdown 层级、代码围栏、链接、图片路径、表格和 YAML frontmatter 都能正常解析。

## 本项目文章的 frontmatter

在修改或新增本项目 `data/articles` 内的文章时，沿用现有 YAML 字段和格式。至少维护 `author`、`category`、`date`、`serialNo`、`status`、`summary`、`tags`、`title`；已有的 `csdn`、`gitee`、`github`、`juejin`、`thumbnail` 字段不要无故删除。日期、编号、分类和链接从上下文获得，缺少时使用待确认占位，不要编造。

## 交付原则

把“简单、能跑、讲清楚自己为什么这么做”放在第一位。可以比标准技术文档更口语，但不能牺牲可复现性；可以保留个人判断，但要把判断和事实分开。若用户只要求风格分析，输出风格画像和可执行规则，不擅自重写文章。

若用户要求判断一篇文章属于哪一类，先给出“主类型 + 可叠加的副类型”，再说明判断依据，最后给出该类型应采用的章节结构；不要只说它“像你的风格”。
