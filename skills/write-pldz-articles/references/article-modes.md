# 文章类型与结构模式

文章类型由“读者看完后要做什么”决定，不由技术主题决定。同一个 Docker 主题可以写成工具分享、技术文章或教程；同一个 ROS2 主题也一样。

## 快速判断

| 读者目标 | 主类型 | 开头应该回答的问题 | 正文重点 | 结尾应该回答的问题 |
| --- | --- | --- | --- | --- |
| 把一个脚本、插件、工具用起来 | 工具分享型 | 它解决了什么麻烦？值不值得用？ | 快速体验、安装、选项、使用示例 | 适合谁？有什么限制？ |
| 理解一个机制、API 或实现方案 | 技术文章型 | 它为什么这样工作？关键设计是什么？ | 概念模型、代码、关键点、取舍 | 这套方案解决了什么？还能怎么改？ |
| 从零完成一个可验证结果 | 教程型 | 需要准备什么？第一步在哪里做？ | 连续步骤、检查点、预期输出、排错 | 我是否完成了？下一步学什么？ |
| 了解作者做了什么并产生兴趣 | 项目介绍型 | 做出了什么？效果和源码在哪里？ | 预览、功能、架构、源码入口 | 当前版本做到什么？以后做什么？ |

如果用户明确说“写教程”，不要因为有完整代码就自动写成技术文章；如果用户说“分享一个工具”，不要用大量原理把读者挡在使用入口之外。

## 工具分享型

### 文章目的

把一个自己做的脚本、插件、配置、命令组合或小工具分享给别人。读者首先关心“能不能直接用、怎么装、怎么调用、能解决什么问题”，不一定需要理解所有实现细节。

### 推荐结构

```text
使用场景/痛点
→ 快速体验或效果
→ 工具能做什么
→ 安装/配置
→ 指令或 API 示例
→ 常用选项
→ 限制、兼容性和后续优化
```

开头可以直接说“SSH 了 Ubuntu 服务器后，这些操作都有指令，但是比较麻烦，所以这里整理一个 bash 脚本”。先让读者看到价值，再展开代码。

### 写作比例

- 说明和代码以“能用”为中心，完整脚本可以先给。
- 只解释会影响使用的配置项和关键逻辑；不要把每一行都变成课程。
- 命令、参数、浏览器版本、系统版本和兼容性要明确。
- 结尾写“适合什么场景、目前没支持什么、后续可以加什么”。

### 代表样本

- `data/articles/code-space/Ubuntu的Bash工具.md`
- `data/articles/code-space/浏览器网络插件.md`
- `data/articles/others/VSCode相关配置.md`
- `data/articles/others/wsl2-service-heartbeat.md`
- `data/articles/others/体验code-server.md`

## 技术文章型

### 文章目的

解释一个概念、通信模型、API 调用方式、代码结构或工程取舍，让读者不仅能复制代码，还能知道代码为什么这样写。它更像“实践中的技术说明”，不等于纯理论文章。

### 推荐结构

```text
实际问题/为什么需要它
→ 最短概念解释
→ 方案选择和边界
→ 最小例子
→ 完整代码或核心代码
→ 关键模块拆解
→ 运行结果/验证
→ 和其他方案的差异、总结
```

可以使用“直接看代码吧，代码比较简单”，但代码后必须补充关键点。例如代理服务器需要分别解释 hop-by-hop headers、HTTP 转发、WebSocket 双向转发；Markdown 流式渲染需要解释为什么不能用整块 `v-html` 刷新。

### 写作比例

- 概念只讲到能支撑后续实现的程度，立刻落到例子。
- 代码可以较长，但要按模块解释“这部分做了什么”。
- 明确事实、个人选择和未验证推测：分别使用“官方文档说明”“这里采用”“理论上”等表达。
- 结尾总结当前方案的边界，并列出可继续优化的方向。

### 代表样本

- `data/articles/chat-playground/Markdown的流式渲染.md`
- `data/articles/chat-playground/Python代理服务器.md`
- `data/articles/chat-playground/对话和图像API简单体验.md`
- `data/articles/cmake/2_CMake语法的基本指令.md`
- `data/articles/ros2/1_2_1_ROS2话题通讯基础.md`
- `data/articles/ros2/1_3_1_ROS2服务通讯.md`

## 教程型

### 文章目的

把读者从一个已知起点带到一个可检查的终点。重点不是“我知道哪些知识”，而是“读者下一步做什么、在哪执行、成功后看到什么”。教程通常是连续系列的一部分。

### 推荐结构

```text
目标和最终效果
→ 前置条件/版本
→ 安装或初始化
→ 第一个最小例子
→ 配置项目
→ 编译/启动
→ 中间检查点
→ 扩展到第二个例子
→ 常见错误和解决办法
→ 小结
```

教程型文章要多写操作位置和检查点：是在宿主机、Docker 容器、ROS2 workspace 还是项目目录里执行；命令成功后应该出现什么；如果没有出现，要检查什么。不要只给一串没有结果说明的命令。

### 写作比例

- 步骤顺序比概念完整更重要，但每一步都要有最少的原因说明。
- 版本和前置依赖放在文章前面；系列文章要承接上篇已有环境。
- 常见错误可以放在主流程之后，以“错误提示 → 可能原因 → 尝试解决办法”组织。
- 结尾明确本篇完成了什么，以及下一篇或下一阶段接什么内容。

### 代表样本

- `data/articles/cmake/1_快速体验VSCode和CMake创建C_C++项目.md`
- `data/articles/ros2/1_1_1_Ubuntu配置与ROS2快速体验.md`
- `data/articles/ros2/2_2_1_Arduino基本语法.md`
- `data/articles/ros2/2_4_1_MicroROS初步体验.md`
- `data/articles/ros2/3_1_1_docker命令熟悉.md`
- `data/articles/ros2/3_2_1_通过Turtlebot3案例了解NAVI2.md`

## 项目介绍型

### 文章目的

展示一个已经做出来的项目、网页或 demo。读者先看效果和源码入口，再决定要不要深入实现。它不是默认的完整教程。

### 推荐结构

```text
项目动机
→ 在线体验/截图/GIF
→ 源码地址
→ 技术栈和整体结构
→ 核心功能
→ 项目结构
→ 运行或部署方式
→ 当前版本范围和后续计划
```

代表样本是 `data/articles/chat-playground/AIGC_Playground_v1.md` 和 `data/articles/code-space/使用VUE3创建个人静态主页.md`。如果用户后续要求“教我从零做这个项目”，再切换为教程型，不能只沿用项目展示结构。

## 混合类型的处理

混合是正常的，但先选主类型：

- 工具分享 + 技术文章：先给快速体验和使用方式，再解释核心实现；适合浏览器插件、Bash 工具、代理服务。
- 技术文章 + 教程：先讲最短概念，再按步骤实现；适合 ROS2 通讯、CMake 配置、MicroROS。
- 项目介绍 + 教程：先展示效果和源码，再选一个核心功能做完整实现；不要把整个项目所有文件都平铺解释。
- 工具分享 + 教程：适合 code-server、Docker 环境；以“装好并跑起来”为终点，不必扩展成完整原理课。

写作前在内部明确一句：“这篇文章的主类型是 X，读者最终要完成 Y。”正文的标题顺序、代码数量和解释深度都围绕这句话调整。
