## 一句话概括

这是“边做边记”的中文技术实践文：作者从一个真实开发动机出发，选择一个尽量简单的方案，直接给出能运行的代码和命令，再用自己的验证结果、报错和判断把读者带完整个过程。

这里的“边做边记”比“开发者风格”更重要。原文不是把每个项目都写成一篇结构完整、价值清晰、未来方向明确的文章；有些地方就是“这里我试了这个”“代码如下”“这个报错这样处理”，写到能用的地方就往下走。

## 稳定特征

### 1. 先讲动机，再讲技术

开头通常不是定义，而是“我在做什么时遇到了什么，所以这里做一个简单实现”。常见方向包括：

- “因为在做 A，免不了出现 B，所以用 C 实现一个简单版本。”
- “这个例子想尽可能简单、容易理解，方便有兴趣的小伙伴继续 fork。”
- “这里采用第二种方式，最简单快速地完成……”

这让文章有明确的实践场景，也自然解释了为什么没有选择更复杂的方案。

但不要把这种开头抽象成模板句“本文旨在解决……”。更接近原文的写法是直接说：

- “因为在做 aigc 的服务免不了出现代理的情况, 所以用 Python 的 `aiohttp` 库来实现一个简单的全代理服务器。”
- “`GPT` 的流输出还是要渲染成 `markdown`, 网络上的教程还是蛮多的,个人打算用 `VUE3` 创建一个调用 `GPT` 的 `stream` 对话的网页。”
- “`SSH` 了 `Ubuntu` 服务器 如果想查看电池电量、监控 `CPU` 和内存使用情况……这里简单的更新一点这个指令 `bash` 脚本。”

这些句子不一定语法最漂亮，但信息是直接的：为什么做、用了什么、现在准备做什么。

### 2. 读者跟着作者一起跑

大量使用“首先”“然后”“此时”“接下来”“那么”“这里”“如下所示”等过程连接词。正文经常按以下路径展开：

```text
前置环境 → 安装/配置 → 最小例子 → 完整代码 → 关键点 → 编译/运行 → 效果 → 问题与总结
```

遇到错误时，先贴出报错，再写“可能的原因”和“尝试解决办法”，而不是假装流程永远一次成功。

### 3. “完整代码优先，解释跟在后面”

文章常直接写“完整的代码如下”或“直接看代码吧”，然后提供一份可以复制的示例。代码块里有中文注释，正文再按“过滤头部”“代理处理函数”“启动应用”这样的关键模块拆解。

对于 ROS2、CMake、Docker 等系列文章，目录树、命令行输出、配置文件、编译命令和运行命令都属于正文的一部分，而不是附录。

### 4. 口语化但不脱离技术现场

适合使用：

- “简单体验”“快速体验”“直接上结果”“话不多说”“没啥好说的”。
- “个人觉得”“我希望”“暂时这样设计”“理论上也支持”“如果大家是其他版本的，建议……”。
- 轻量 emoji，用在标题、体验、提示和结果位置：`😎`、`🔧`、`🚀`、`💡`、`🎉`。

不要让每段都出现口头禅，也不要把文章写成营销文案。轻松感来自真实开发过程和作者判断，不来自大量感叹号。

### 5. 直接写现象，不替读者做价值总结

你的文章会写“目前已在以下浏览器中测试”“理论上也支持，但没有去测试”“如果没有 gazebo 和 rviz2 的需要再次安装”“这个没啥好说的，就一个信号线”。这些话把信息和经验直接放出来，不专门把它们包装成“兼容性优势”“最佳实践”或“使用价值”。

输出文章时优先采用：

```text
目前只在 Ubuntu X11 下测试过，Wayland 还没有支持，其他 Linux 发行版也没有测试。
```

不要主动改成：

```text
这个项目暂时只在 Ubuntu X11 环境中测试过。它的目标不是做一个完整的语音助手，而是先把链路跑通，方便后面继续扩展。
```

后一句多了“目标—范围—未来”的完整叙事，语气就会从开发记录变成 AI 项目介绍。除非输入材料确实表达了这层意思，否则不要补。

### 6. 中英文技术词自然混排

保留原项目中的习惯：中文叙述中直接出现 `Python`、`VUE3`、`ROS2`、`C/C++`、`Dockerfile`、`stream`、`Node`、`workspace` 等；命令、包名、路径、配置键使用反引号。不要为了语言统一把技术名词全部翻译成中文。

### 7. 结构有系列感，也允许实录式不规整

长系列常使用 `1.1`、`1.2.1`、`2.5.3` 这样的编号，内容从概念逐步推进到 C/C++、Python、硬件或 Docker 实例。单篇项目文章则常用“前言 / 体验 / 具体实现 / 总结”，并配合图片、GIF、项目链接。

标题可以带少量 emoji；如果文章属于已有系列，优先遵循系列编号。不要为了规整而添加空洞的“本文小结”或硬凑层级。

## 句式和节奏

推荐采用以下节奏：

1. 一段简短的场景说明。
2. 一句个人选择或限制条件。
3. 一个命令、代码块、目录树或截图。
4. 一小段解释“这部分做了什么 / 为什么这样写”。
5. 一个可以观察结果的动作。

段落不宜堆太多抽象定义。概念需要出现时，用一个项目或 demo 立刻落地，例如先说明“话题通信是一种单向通信模型”，紧接着给发布方、订阅方和运行方式。

## 需要保留的“不完美感”与需要修正的错误

可以保留：

- 第一人称、直接称呼读者、稍微口语的转折。
- 中英文混排和技术现场的命令行语气。
- “简单版本”“暂时这样设计”“后续优化”这类范围意识。

应该修正或明确标注：

- 会导致读者执行失败的包名、函数名、路径、版本和命令错误。
- 把“理论上支持”写成“已经测试”的表述。
- 未提供真实截图时虚构的效果图、日志或部署结果。
- 暴露真实 API key、内网地址、密码、个人机器绝对路径。

目标是保留作者的声音，不是复制错别字或制造不可靠的教程。

## 常见文章模板

### 项目或功能介绍

```markdown
# 🌟 项目名称

一句话说明项目想解决什么问题。

## 👀 效果预览
在线体验、源码、截图或 GIF

## 🚀 技术实现
整体结构和技术选择

## 🔨 核心功能
按功能给出代码和解释

## 📁 项目结构
目录树和每个文件的作用

## 🚀 运行或部署
命令、环境变量和验证结果

## 📖 总结
目前完成什么，没做什么，后续想怎么优化
```

### 工具或环境实践

```markdown
# 工具名称

## 0. 先直接体验 / 前置条件
## 1. 安装
## 2. 配置
## 3. 最小例子
## 4. 运行结果
## 5. 可能出现的问题
## 6. 总结
```

### 基础知识系列

```markdown
# 2.1 概念名称

概念的最短解释 + 一个真实使用场景

# 2.2 常用内容
## 2.2.1 第一个最小例子
## 2.2.2 配置功能包或项目
## 2.2.3 编译并运行
## 2.3 使用另一种语言或方案
## 2.4 小结
```
